长期慢场景下的 outbound queue 策略说明

本文档用于回答两个问题：

1. 如果 peer 长期慢，为什么仍然要用有界队列
2. 有界队列满了以后，应该采用什么策略


## 1. 先说结论

如果 peer 是“长期慢”，那么：

- 无界队列一定不是解法
- 有界队列反而是必须的

原因不是因为有界队列能让 peer 变快，而是因为：

- 有界队列能阻止“慢”演化成“内存无限上涨”
- 有界队列能逼系统进入明确的退化策略

也就是说：

- 慢本身不一定能马上修掉
- 但系统必须先做到“慢的时候也不会崩”


## 2. 为什么长期慢会导致内存一直涨

如果长期出现：

- 上游生产速率 > 下游消费速率

那么中间的 backlog 就会持续累计。

如果这时候使用的是无界队列，那么结果就是：

- 先表现为内存平稳上升
- 再表现为 RSS 长时间不回落
- 最终可能演化成 OOM、抖动、严重 GC/allocator 压力或进程失稳

所以无界队列的问题不是“能不能跑一阵子”，而是：

- 它只是把供需失衡延后暴露
- 代价是用内存硬扛


## 3. 为什么有界队列反而适合长期慢

长期慢说明问题不是瞬时波动，而是容量不匹配。

这时有界队列的价值在于：

1. 明确系统容量上限
2. 避免 backlog 无限增长
3. 强制系统选择退化方式
4. 让问题更早暴露、更容易观测

所以有界队列不是“解决慢”，而是“控制慢带来的损害”。


## 4. 队列满了以后，系统只能做什么

如果系统长期超产，就不可能同时满足这四件事：

1. 不丢消息
2. 不阻塞上游
3. 不涨内存
4. 吞吐还保持不变

这是不可能同时成立的。

因此，队列满了以后，系统必须在下面几种策略中选一个或几个组合：

- 阻塞上游
- 丢弃消息
- 覆盖旧消息
- 降级慢 peer
- 落盘


## 5. 常见策略一：阻塞上游

做法：

- bounded channel 满了以后
- 使用 `send().await`
- 让上游生产方变慢

含义：

- 不再继续无界积压
- 把背压一路传递回上层

优点：

- 不丢消息
- 最符合“关键消息必须送达”的语义
- 内存稳定

缺点：

- 整体吞吐下降
- 尾延迟变高
- 如果上游也很关键，可能进一步影响更外层流程

适用：

- 关键消息
- 不能丢失的业务消息
- 更重视一致性而不是峰值吞吐的场景


## 6. 常见策略二：丢弃消息

做法：

- bounded channel 满了以后
- 使用 `try_send`
- 失败就丢弃并打日志/metrics

含义：

- 系统选择保护整体稳定性
- 接受部分消息无法发出

优点：

- 实现简单
- 不会把背压传播得很深
- 内存可控

缺点：

- 会丢消息
- 需要业务接受失败语义

适用：

- 广播类消息
- 非关键通知
- 冗余同步消息


## 7. 常见策略三：覆盖旧消息，只保留最新值

做法：

- 队列里已有旧状态消息时
- 新状态到来后覆盖旧状态
- 不保留完整历史

含义：

- 目标不是保证每条消息都到
- 而是保证最终状态尽快到达

优点：

- 对状态同步类场景特别有效
- 可以极大减少积压

缺点：

- 不适用于必须逐条处理的消息
- 需要业务语义允许“旧消息被跳过”

适用：

- 最新区块高度
- 最新状态通知
- 配置同步
- 心跳/快照类消息


## 8. 常见策略四：对慢 peer 降级

做法：

- 某个 peer 连续超时或持续慢
- 降低其优先级
- 暂停给它发某类广播
- 或者直接断开连接

含义：

- 承认不是所有 peer 都值得同等资源
- 用局部退化换整体稳定

优点：

- 对少数异常 peer 特别有效
- 可以避免整个系统被个别坏 peer 拖垮

缺点：

- 被降级的 peer 可能收不到部分消息
- 策略判断需要额外标准

适用：

- 广播网络
- peer 数量较多
- 存在个别明显慢节点的场景


## 9. 常见策略五：落盘

做法：

- 内存队列满了以后
- 不直接丢弃
- 把消息持久化到磁盘，后续异步重放

含义：

- 用磁盘容量替代内存容量
- 适用于不能轻易丢消息的场景

优点：

- 可以避免内存失控
- 比纯丢弃更保守

缺点：

- 改动大
- 实现复杂
- 磁盘 I/O、恢复逻辑、顺序语义都要处理

适用：

- 关键且不能丢失的消息系统
- 但不适合作为当前问题的“小改动修复”


## 10. 对本项目最现实的选择

如果只考虑当前问题，并且要求：

- 改动小
- 风险低
- 易验证

那么最现实的组合通常是：

1. 限制 broadcast fan-out 并发
2. per-peer outbound queue 改为 bounded
3. 对广播类消息队列满时直接失败或丢弃
4. 给发送加超时
5. retry queue 也加上限

这个组合的核心思想是：

- 让慢变成受控失败
- 而不是让慢变成无界内存上涨


## 11. 各策略的直观对比

### 11.1 阻塞上游

- 不丢消息
- 吞吐下降
- 延迟升高
- 内存最稳定

### 11.2 丢弃消息

- 实现简单
- 稳定性高
- 会损失部分消息
- 适合广播类场景

### 11.3 覆盖旧消息

- 对状态类消息效果最好
- 可极大压缩积压
- 不适合逐条语义消息

### 11.4 慢 peer 降级

- 对局部坏 peer 特别有效
- 不影响全部 peer
- 需要定义降级标准

### 11.5 落盘

- 保守
- 复杂
- 不适合作为第一阶段小修


## 12. 如何选择

可以按消息类型来分：

### 12.1 如果消息不能丢

优先考虑：

- bounded queue
- 背压上游
- 必要时再考虑落盘

### 12.2 如果消息可以丢

优先考虑：

- bounded queue
- `try_send`
- 丢弃并记录 metrics

### 12.3 如果消息只关心最新状态

优先考虑：

- 覆盖旧消息
- 只保留最新值

### 12.4 如果只有少数 peer 慢

优先考虑：

- 慢 peer 降级
- 限制其队列
- 连续超时后断开


## 13. 对当前 `OutboundMessage` 问题的建议

如果你现在已经确认问题更像：

- `OutboundMessage` 堆积
- 而不是对象真泄露

那么第一阶段最值得做的是：

1. 保留当前 Prometheus 指标
2. 限制 `broadcast` 的内部并发
3. 把 per-peer queue 改成 bounded
4. 对队列满的广播类消息直接失败或丢弃
5. 观察：
   - `outbound_pending_messages`
   - `retry_queue_messages`
   - `enqueue_count - dequeue_count`

如果改完以后：

- 内存不再持续单边上涨
- `outbound_pending_messages` 只在平台附近波动

那么说明方向是对的。


## 14. 一句话结论

长期慢不是“不适合有界队列”的理由，恰恰相反：

- 长期慢越明显，越必须使用有界队列

因为系统最终必须在这些选项中做选择：

- 阻塞
- 丢弃
- 覆盖
- 降级
- 落盘

而不能继续依赖无界队列用内存硬扛。
